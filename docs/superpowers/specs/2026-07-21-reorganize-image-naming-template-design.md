# 整理图片资源时应用命名模板设计

## 背景

当前 `imageNamingTemplate` 只在粘贴或拖放图片时生效。执行“整理图片资源”时，`ImageReorganizer` 只根据图片路径模板移动文件，始终保留原文件名。因此，已经存在于 Vault 中的图片即使配置了命名模板，也不会按照该模板重命名。

本设计让资源整理与粘贴/拖放共用同一套图片命名规则，同时保证目标目录中的已有文件不会被覆盖，并正确更新跨笔记引用。

## 目标

- 整理图片资源时读取当前配置的完整 `imageNamingTemplate`。
- 只替换模板中实际出现的变量，不强制添加 `{timestamp}` 或其他变量。
- 单次整理任务中的 `{counter}` 从 `0` 开始，并按不同图片连续递增。
- 生成目标名称前检查目标目录和本次任务预留的名称，任何情况下都不覆盖已有文件。
- 单篇笔记整理和文件夹整理使用一致的命名、冲突处理及引用更新行为。
- 粘贴/拖放与资源整理共用命名模板解析和文件名清理逻辑。
- 图片被同一笔记多次引用或被多篇笔记引用时，只重命名一次，并更新所有相关引用。

## 非目标

- 不新增命名模板设置项或模板变量。
- 不修改图片扩展名或图片内容。
- 整理时不弹出手动输入图片名称的窗口。
- 不改变图片路径模板、引用格式转换或跳过 Wiki 引用的现有设置语义。
- 不对与本功能无关的整理、批量重命名或引用解析模块进行重构。

## 现有行为

### 粘贴和拖放

`src/main.ts` 中的 `generateFileName` 使用以下变量渲染 `imageNamingTemplate`：

- `{date}`
- `{time}`
- `{timestamp}`
- `{year}`
- `{month}`
- `{day}`
- `{counter}`

渲染完成后，`sanitizeFileName` 会移除扩展名、替换空白、删除不安全字符并补回原扩展名。

### 资源整理

`src/utils/image-reorganizer.ts` 当前直接使用 `imageFile.name` 计算目标路径。因此整理只会移动图片，不会根据 `imageNamingTemplate` 生成新名称。冲突时仅在原文件名后追加 `-1`、`-2`。

## 方案选择

采用共享命名模板解析器。粘贴/拖放和资源整理共同调用一个纯工具模块；整理器继续负责任务级计数、目标路径分配、移动和引用更新。

没有采用以下方案：

- 在 `ImageReorganizer` 内复制命名逻辑：实现简单，但两套规则容易漂移。
- 整理时逐张调用 `BatchRename`：会为每张图片重复扫描整个 Vault，批量整理性能差，且移动和重命名时序更复杂。

## 模块设计

### 共享命名模板工具

新增 `src/utils/image-name-template.ts`，职责如下：

- 根据传入的模板、时间、计数器和扩展名生成文件名。
- 仅替换模板中已支持且实际出现的变量；未出现的变量不参与结果。
- `{date}`、`{time}`、`{timestamp}`、`{year}`、`{month}`、`{day}` 在模板包含对应占位符时，使用生成该图片候选名称时的当前时间。
- 保留原图片扩展名；如果模板包含同扩展名，则先移除再统一补回，避免重复扩展名。
- 统一执行现有文件名清理规则：空白转连字符、移除不安全字符、合并连续连字符、去除首尾连字符。
- 模板清理后为空时，回退为 `image`。

该模块保持纯函数形式，使时间和计数器可以在测试中显式传入。

### 整理任务上下文

`ImageReorganizer` 为每次公开整理命令创建独立上下文，至少包含：

- `nextCounter`：下一个可尝试的模板计数值，初始为 `0`。
- `reservedPaths`：本次任务已经分配但可能尚未移动的目标路径。
- `plannedImages`：源图片到目标路径的规划，避免同一图片被重复分配。
- `successfulMoves`：实际成功的旧路径到新路径映射，用于引用更新。
- `failures`：移动失败记录，用于最终结果提示。

单篇笔记整理创建一次上下文。文件夹整理也只创建一次上下文，并在其中处理所有笔记，因此 `{counter}` 不会在每篇笔记之间重置。

### 结果类型

`ReorganizeResult` 增加失败数量，以便区分无法解析或被设置跳过的引用与实际移动失败：

```typescript
interface ReorganizeResult {
    moved: number;
    skipped: number;
    failed: number;
}
```

文件夹结果继续附加 `notes`。最终通知显示成功、跳过和失败数量；错误内容通过现有国际化机制提供中文和英文文案。

## 名称与目标路径分配

### 基本流程

对每张不同的源图片执行以下步骤：

1. 读取当前 `settings.imageNamingTemplate`。
2. 使用当前候选计数值和图片原扩展名渲染完整模板。
3. 使用生成后的文件名解析 `imagePathTemplate`，得到目标目录。
4. 拼接目标目录与候选文件名，得到候选目标路径。
5. 检查候选目标路径是否可用。
6. 可用时预留路径；不可用时按照冲突规则继续尝试。

目标目录必须基于最终候选文件名重新解析，因为 `imagePathTemplate` 支持 `{filename}`。

### 可用性判断

满足以下任一条件时，候选路径可接受：

- 候选路径就是当前源图片自身的路径。
- Vault 内存映射和底层适配器中都不存在该路径，并且 `reservedPaths` 中也没有该路径。

候选路径存在且属于其他文件时，即使该文件也计划在稍后移走，仍然视为冲突。这样可以保证执行顺序不会造成覆盖或路径交换风险。

### 模板包含 `{counter}`

发生冲突时递增候选计数器，重新渲染整个命名模板，并重新计算目标目录和目标路径。例如：

```text
模板：image-{counter}
已存在：image-0.png
尝试：image-1.png
```

某张图片接受计数值 `n` 后，下一张不同图片从 `n + 1` 开始。冲突过程中跳过的计数值不会被后续图片重新使用。

### 模板不包含 `{counter}`

先尝试模板直接生成的基本名称。发生冲突时，在基本名称与扩展名之间追加递增后缀：

```text
photo.png
photo-1.png
photo-2.png
```

后缀检查同样考虑 Vault 内存映射、底层适配器和本次任务预留路径，避免缓存尚未同步时覆盖磁盘中的已有文件。

## 整理数据流

### 规划阶段

1. 解析本次整理范围内的图片引用。
2. 根据现有设置跳过外部 URL 和不应处理的 Wiki 引用。
3. 将引用解析为实际 `TFile`，并按源文件去重。
4. 为每张不同图片分配唯一目标路径。
5. 记录引用与源图片的对应关系，供移动后精确更新。

同一图片被多次引用时沿用第一次分配的目标路径，不再次消耗 `{counter}`。

### 执行阶段

1. 创建所有需要的目标目录。
2. 每次调用 `vault.rename` 前再次检查目标路径。
3. 如果规划后出现新的同名文件，继续按相同规则分配下一个可用名称。
4. 重新分配后同步替换旧的预留路径和该图片的目标规划，保证后续引用使用最终路径。
5. 只有移动或重命名成功后，才写入 `successfulMoves`。
6. 单张图片失败时保留其原文件和原引用，记录失败后继续处理其余图片。

目标路径等于源路径时不调用 `vault.rename`，也不计入 `moved`。

### 引用更新阶段

1. 根据 `successfulMoves` 构建旧路径到新路径的映射；无需移动但需要转换格式的范围内引用单独保留在引用更新计划中。
2. 重新读取可能受影响的笔记，避免使用移动期间已经过期的内容快照。
3. 更新当前整理范围内及其他笔记中指向已移动图片的引用。
4. Markdown 引用根据 `imagePathBase` 生成 Vault 路径或相对路径，并使用现有 `encodePathSegments` 规则编码。
5. Wiki 引用使用新文件名；已有别名保持不变。
6. Markdown alt 文本保持不变。
7. 如果 `reorganizeConvertFormat` 要求转换为 Markdown，则继续执行现有格式转换行为。
8. 已经由 Obsidian 更新到正确目标的引用直接跳过，避免重复写入。

格式转换不依赖文件是否移动：目标路径等于源路径时，仍会按现有设置转换本次整理范围内的引用。图片移动失败时则保持该图片的原引用和原格式。

引用更新基于规划阶段解析出的实际源文件和成功映射，不再仅依赖移动后的文件名反查，因此图片改名后仍可更新跨笔记引用。

## 异常处理

- 目标目录存在同名文件时永不覆盖，继续分配下一个候选名称。
- 规划后新出现冲突时，在实际移动前重新分配名称。
- 模板结果为空或只包含非法字符时使用 `image`。
- 目录创建或文件移动失败只影响对应图片；该图片保持原引用。
- 只为成功移动的图片更新引用。
- 单张失败不阻止其余图片继续整理。
- 无法解析的引用继续计入 `skipped`，与移动失败的 `failed` 分开统计。

## 设置与文案

不新增设置。修改现有命名模板说明，使其从“粘贴/拖放图片时的命名模板”扩展为“粘贴、拖放和整理图片资源时的命名模板”。

中英文文案保持相同变量集合，并为整理结果增加失败数量的插值变量。

## 测试设计

### 命名模板工具测试

- 逐一验证所有现有变量的替换。
- 验证只使用模板中实际存在的变量。
- 验证不自动添加 `{timestamp}` 或其他变量。
- 验证原扩展名保留且不会重复。
- 验证空白、不安全字符、连续连字符和空结果的清理行为。
- 通过固定时间和计数器验证结果可重复。

### 整理器测试

- `{counter}` 在单篇笔记整理中从 `0` 开始并连续递增。
- 文件夹整理只创建一个任务上下文，计数器不会按笔记重置。
- 目标目录已有 `image-0.png` 时从 `image-1.png` 继续尝试。
- 模板不含 `{counter}` 时使用 `-1`、`-2` 后缀。
- 本次任务预留但尚未移动的路径也会触发冲突。
- 候选路径等于源图片自身时不移动、不视为冲突。
- 已有文件永不被覆盖，内容和路径保持不变。
- 同一图片被多次引用时只分配一次名称。
- 跨笔记共享图片重命名后，所有相关引用均更新。
- 移动失败时原引用保留，其他图片继续处理，并增加失败计数。
- Markdown 相对路径、Vault 路径、Wiki 引用和格式转换行为保持正确。

### 回归验证

- 粘贴和拖放继续使用配置模板生成名称。
- 现有路径编码、引用转换和图片路径模板测试继续通过。
- 运行 `npm test`。
- 运行 `npm run build`，覆盖 ESLint、TypeScript 检查和生产构建。
